# ARTIFACTS.md

Перечень артефактов и протоколов проекта **KALKULATOR**

---

## 1. Введение

**Назначение документа.** Документ содержит полный перечень файлов и каталогов, из которых состоит проект «KALKULATOR», с указанием их назначения, типа и того, хранятся ли они в системе контроля версий. Вторая часть документа описывает протоколы — правила, по которым модули проекта обмениваются данными, и соглашения, которых придерживается команда при именовании и версионировании.

**Область применения.** Документ предназначен для участников команды разработки. Он используется:

- при подключении нового участника к проекту — чтобы быстро понять состав репозитория;
- при интеграции модулей — чтобы вызывать чужой код по согласованному контракту, а не по догадкам;
- при проверке репозитория — чтобы убедиться, что в Git не попали лишние файлы.

**О проекте.** «KALKULATOR» — настольное приложение (Windows, C#, WPF/.NET Framework). Калькулятор с двумя режимами: обычным (`MainWindow`) и инженерным (`EngineerCalculator`). Вычисления выполняет `CalculatorService`, историю вычислений сохраняет в текстовый файл `HistoryLog`.

**База данных в проекте не используется** — история вычислений хранится в обычном текстовом файле. Поэтому протоколы доступа к БД в документе отсутствуют.

## 3. Протоколы взаимодействия между модулями

Протоколы определены на основе диаграммы компонентов из ЛР №2. Направление всех зависимостей: `App → Views → Services`.

### Протокол 1. `ICalculatorService` — вычисления

| | |
|---|---|
| **Название** | `ICalculatorService` |
| **Участники** | `Views` (`MainWindow`, `EngineerCalculator`) → `Services.CalculatorService` |
| **Назначение** | Выполнение арифметических и математических операций над введённым выражением |

**Интерфейс:**

```csharp
string Calculate(string expression);   // вычисление выражения целиком
string CalculateSquare(string input);  // возведение в квадрат
string CalculateSqrt(string input);    // квадратный корень
string CalculateReciprocal(string input); // обратное число 1/x
string CalculatePercent(string input); // процент
string CalculateSin(string input);     // синус
string CalculateCos(string input);     // косинус
string CalculateTan(string input);     // тангенс
string CalculateCtg(string input);     // котангенс
string CalculateExp(string input);     // экспонента
```

**Формат обмена данными:** обычные строки C# (`string`) в обе стороны. Сериализация (JSON, XML) не применяется, так как оба модуля работают в одном процессе.

**Правила и ограничения:**

- на вход подаётся текст ровно в том виде, в каком он введён в поле `ResultDisplay`;
- десятичный разделитель — **запятая** (`,`); модуль сам заменяет её на точку перед вычислением;
- знак степени в выражении — `^`; модуль сам заменяет его на `**`;
- углы тригонометрических функций передаются **в градусах**, перевод в радианы выполняется внутри сервиса;
- **ошибки не выбрасываются исключениями.** При некорректном вводе, делении на ноль или корне из отрицательного числа метод возвращает строку `"Ошибка"`. Вызывающая сторона обязана учитывать, что результат может не быть числом;
- пустая строка на входе метода `Calculate` даёт результат `"0"`.

### Протокол 2. `IHistoryService` — журнал вычислений

| | |
|---|---|
| **Название** | `IHistoryService` |
| **Участники** | `Views` (`MainWindow`, `EngineerCalculator`) → `Services.HistoryLog` |
| **Назначение** | Сохранение, чтение и очистка истории вычислений |

**Интерфейс:**

```csharp
void SaveToLog(string newtext);  // добавить запись в конец журнала
string ReadLog();                // прочитать журнал целиком; null, если файла нет
bool ClearLogFile();             // удалить журнал; true — удалён, false — файла не было
```

**Формат обмена данными:** строки C#. Хранилище — текстовый файл `calculator_log.txt`, по одной записи на строку:

```
17.09.2026 14:32:05: 2+2=4
```

То есть: `дата и время` + `: ` + `выражение` + `=` + `результат`.

**Правила и ограничения:**

- запись добавляется в конец файла, существующие строки не изменяются;
- отметку времени проставляет сам модуль — вызывающей стороне передаётся только строка вида `выражение=результат`;
- `ReadLog()` возвращает `null`, если файла ещё нет; вызывающая сторона обязана проверять результат на `null`;
- `ClearLogFile()` возвращает `false`, если удалять нечего — это не ошибка;
- путь к файлу задан внутри модуля константой, поэтому журнал создаётся в рабочем каталоге приложения.

### Протокол 3. Переключение режимов и передача оформления

| | |
|---|---|
| **Название** | Протокол переключения режимов |
| **Участники** | `Views.MainWindow` ↔ `Views.EngineerCalculator` |
| **Назначение** | Переход между обычным и инженерным режимом с сохранением выбранной пользователем цветовой схемы |

**Интерфейс:**

```csharp
MainWindow(Brush bg, Brush btn, Brush font);
EngineerCalculator(Brush bg, Brush btn, Brush font);
```

**Формат обмена данными:** три объекта типа `System.Windows.Media.Brush` — цвет фона окна, цвет кнопок, цвет текста.

**Порядок взаимодействия:** по нажатию кнопки «Режим» текущее окно создаёт окно другого режима, передавая ему три текущих цвета через конструктор, вызывает `Show()` у нового окна и `Close()` у себя.

**Ограничение (известный недостаток).** Окна создают друг друга напрямую, из-за чего между ними возникает взаимная (циклическая) зависимость. Это нарушает правило «зависимости направлены сверху вниз». Планируемое решение — вынести переключение в отдельный модуль `INavigationService`, от которого будут зависеть оба окна.

### Протокол 4. События

Собственных событий (`event`) модули проекта **не публикуют**. Всё взаимодействие построено на прямых вызовах методов.

Единственный используемый механизм событий — **стандартные события WPF**, связывающие разметку `.xaml` с кодом `.xaml.cs` внутри одного модуля:

| Событие | Где возникает | Обработчик |
|---|---|---|
| `Click` | кнопки цифр | `NumButton_Click` |
| `Click` | кнопки операций | `OpButton_Click` |
| `Click` | кнопка «=» | `ResultButton_Click` |
| `Click` | кнопки функций (sin, cos, √ …) | `Sin_Click`, `Cos_Click`, `Sqrt_Click` … |
| `Click` | кнопка «История» | `History_Click` |
| `Click` | кнопка «Режим» | `Change_Click` |
| `SelectionChanged` | выбор зоны раскраски | `ColorZone_SelectionChanged` |

Имя обработчика формируется по правилу: `ИмяЭлемента_ИмяСобытия`.

## 4. Соглашения об именовании и версионировании

### 4.1. Код на C#

| Элемент | Правило | Пример |

Расхождения зафиксированы для исправления.

### 4.2. Файлы и каталоги

- один класс — один файл, имя файла совпадает с именем класса: `HistoryLog.cs`;
- окно состоит из пары файлов: `Имя.xaml` и `Имя.xaml.cs`;
- каталог соответствует пространству имён: `Views/`, `Services/`;
- документация — заглавными буквами в корне: `README.md`, `ARTIFACTS.md`.

### 4.3. Ветки Git

| Тип ветки | Шаблон | Пример |
|---|---|---|
| Основная | `main` | `main` |
| Новая возможность | `feature/краткое-описание` | `feature/engineer-mode` |

Слова разделяются дефисом, только строчные латинские буквы. Прямые коммиты в `main` не выполняются — изменения вливаются через pull request.

### 4.4. Сообщения коммитов

Принят формат **Conventional Commits**: `тип: краткое описание в повелительном наклонении`.

| Тип | Когда используется |
|---|---|
| `feat` | добавлена новая возможность |
| `fix` | исправлена ошибка |
| `docs` | изменена только документация |
| `refactor` | код переработан без изменения поведения |
| `style` | форматирование, без влияния на логику |

Примеры:

```
docs: добавить перечень артефактов и протоколов
fix: исправить сравнение зоны раскраски с "Фон окна"
feat: добавить кнопку экспоненты в инженерный режим
```

Первая строка — не длиннее 72 символов, без точки в конце.

### 4.5. Версионирование

Используется семантическое версионирование **SemVer**: `МАЖОРНАЯ.МИНОРНАЯ.ПАТЧ`.

| Часть | Увеличивается, когда | Пример |
|---|---|---|
| МАЖОРНАЯ | изменения ломают совместимость, например меняется сигнатура метода в `ICalculatorService` | `1.0.0 → 2.0.0` |
| МИНОРНАЯ | добавлена новая возможность, старый код продолжает работать | `1.0.0 → 1.1.0` |
| ПАТЧ | исправлена ошибка, поведение не изменилось | `1.1.0 → 1.1.1` |

- версия сборки указывается в `Properties/AssemblyInfo.cs` в атрибутах `AssemblyVersion` и `AssemblyFileVersion`;
- каждой выпущенной версии соответствует тег в Git с префиксом `v`: `v1.0.0`, `v1.1.0`;
- пока проект не выпущен, мажорная часть равна `0` — версия `0.x.y` означает, что интерфейсы ещё могут меняться.

## 5. Заключение

В документе проведена инвентаризация проекта «KALKULATOR»: перечислены все файлы и каталоги, каждому определены назначение, тип, категория, этап жизненного цикла и признак хранения в Git. Артефакты разделены на шесть категорий — исходный код, конфигурация, документация, сборка, данные времени выполнения и вспомогательные.

Проверка показала, что производные артефакты (`bin/`, `obj/`, `.vs/`, `*.user`) и файл истории вычислений в репозиторий попадать не должны, и предложено содержимое `.gitignore`, которое это гарантирует. Отдельно зафиксировано отсутствие тестового проекта и сценариев автоматической сборки — это направление дальнейшего развития проекта.

Описаны три протокола взаимодействия между модулями: `ICalculatorService`, `IHistoryService` и протокол переключения режимов. Для каждого указаны участники, назначение, состав методов, формат передаваемых данных и ограничения. При описании выявлены два недостатка: взаимная зависимость между окнами режимов и передача ошибок строкой `"Ошибка"` вместо исключения. Оба замечания зафиксированы как задачи на доработку.

Приняты и записаны соглашения об именовании классов, методов, файлов, веток Git и сообщений коммитов, а также правила версионирования по схеме SemVer. Наличие этих соглашений в репозитории позволяет новому участнику команды подключиться к работе, не выясняя правила у остальных, и делает интеграцию модулей предсказуемой.
